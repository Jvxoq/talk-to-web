# Define the whole suite before building it

Teams at Anthropic, OpenAI and other companies that run LLM products describe a whole **suite** (the full set of tasks run together) with six properties. First, it has a stated purpose: a regression group that stays near 100%, and a capability group that starts low. Second, its tasks come from real failures and real traffic, not from imagined risks. Third, each task is fair, solvable and balanced both ways. Fourth, every trial (one attempt at a task) starts clean, and results are shown per task, not only as one average. Fifth, every grader (the code or model that scores a trial) is checked, and people read transcripts (the full record of a trial). Sixth, the suite keeps changing: failures from production become new tasks, and saturated tasks leave. One more point comes from the statistics notes. The number of tasks, not the number of trials, sets how small a change the suite can detect. This report lists these properties with sources, then ends with a checklist you can review a build against. It also names where your current plan conflicts with the sources. Most conflicts come from one fact: 3, 10 or even 100 trials cannot prove a 97% pass rate.

**How to read the sources.** Every page in the notes was read through WebFetch, which returns a summary written by a small model. So quotes may be wrong in small ways, and some are paraphrase. Re-check wording on the page before you quote it in public. Pages not opened directly are named in the last section of this report. Anthropic's "Demystifying evals for AI agents" is the main source. Where I write "computed", the math is mine or the notes author's, not a source claim.

## Suites have a declared purpose, and two groups

Anthropic splits suites by target. Capability evals "should start at a low pass rate", and regression evals should sit near 100% ([Anthropic: Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). The notes mark the first wording as a paraphrase, not confirmed verbatim. A capability task that passes often can "graduate" into the regression group (same page). Saturation means the agent passes every solvable task, so the suite no longer shows progress. A suite at 100% only guards against drops. Anthropic gives no number for when to graduate a task.

Practitioners agree, with a different number. Hamel Husain says a 100% pass rate likely means you are not challenging the system, and that about 70% may be more useful ([Hamel evals FAQ](https://hamel.dev/blog/posts/evals-faq/)). He also says the pass threshold is a product decision about tolerable failures ([Hamel: your AI product needs evals](https://hamel.dev/blog/posts/evals/)). The notes treat the 70% versus 100% gap as two different groups, not a real conflict. Notion uses the same split, with regression evals and frontier evals ([Braintrust: Notion](https://braintrust.dev/customers/notion)). That page is a vendor customer story. LangChain adds two ideas: the suite "should not grow monotonically", and it keeps a must-always-pass subset ([LangChain: Better Harness](https://www.langchain.com/blog/better-harness-a-recipe-for-harness-hill-climbing-with-evals)).

OpenAI starts earlier, with the goal. Its five steps are: define the objective, collect a dataset, define metrics, run and compare, and evaluate continuously ([OpenAI: Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)). Anthropic's docs agree that criteria must be specific and measurable. They give one bad example, "Safe outputs", and one good example, under 0.1% of 10,000 trials flagged ([Anthropic: Define success](https://platform.claude.com/docs/en/test-and-evaluate/define-success)). The same docs say most use cases need several criteria at once.

## Tasks come from real failures, and each task must be fair

The strongest agreement across sources is where tasks come from. Anthropic says 20 to 50 simple tasks drawn from real failures is a great start ([Anthropic: Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Hamel calls error analysis (reading traces and naming failure modes) the most important activity in evals, and says to review at least 100 diverse traces ([Hamel evals FAQ](https://hamel.dev/blog/posts/evals-faq/)). He warns that generic evaluations "waste time and create false confidence" (same page). Husain and Shankar say to keep under about 10 failure modes and to write one check per observed mode ([Lenny's Newsletter](https://www.lennysnewsletter.com/p/building-eval-systems-that-improve)). That page is partly paywalled. OpenAI's flywheel cookbook starts from about 50 failing traces and groups them into failure categories ([OpenAI: Evaluation flywheel](https://developers.openai.com/cookbook/examples/evaluation/building_resilient_prompts_using_an_evaluation_flywheel)). Airbnb and Notion also start from real failures ([Airbnb](https://airbnb.tech/ai-ml/eval-driven-development-lessons-from-evaluating-genai-at-scale/), [Braintrust: Notion](https://braintrust.dev/customers/notion)). OpenAI names the opposite as a pitfall: datasets that do not match production traffic ([OpenAI: Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)). GitHub warns that a cleaner dataset that drops ambiguous items inflates scores ([GitHub: evaluate LLMs before production](https://github.blog/2026-08-25-how-to-evaluate-llms-before-production/)).

A task must also be fair. Anthropic says a good task is one where two domain experts would reach the same pass/fail verdict independently, and each task should have a reference solution that passes all graders ([Anthropic: Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). A 0% pass rate over many trials usually signals a broken task or grader, not a weak agent (same page). "One-sided evals create one-sided optimization", so test both when a behavior should and should not happen (same page). OpenAI's SWE-bench Verified work found that vague issues and over-specific tests wrongly fail valid solutions, and that environment faults must be separated from solution quality ([OpenAI: SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/)). OpenAI also says test data should include typical, edge and adversarial cases ([OpenAI: Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)). Anthropic's notes add that the suite is a living artifact with clear ownership, and that keeping it up should be as routine as maintaining unit tests ([Anthropic: Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

## Graders and trials decide whether the numbers mean anything

Sources prefer cheap, exact checks first. Hamel says to favor assertions over LLM judges in CI datasets ([Hamel evals FAQ](https://hamel.dev/blog/posts/evals-faq/)). Vercel's primer says to start with the cheapest check that can catch the failure ([Vercel primer](https://vercel.com/i/ai-agent-evaluation-frameworks-production)). Its figures are secondhand, from a vendor page. Anthropic lists code, model and human graders and prefers code where possible. It says to grade what the agent produced, not the path it took, and to read the transcripts ([Anthropic: Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).

When a model judge is needed, the sources ask for proof. Anthropic says judges "should be closely calibrated with human experts" (same page). OpenAI says to scale a judge once it consistently agrees with human labels ([OpenAI: Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)). Hamel gives the most detail: one judge per failure type, binary verdicts, a held-out test split, and true positive and true negative rates. He suggests about 30 to 50 pass and 30 to 50 fail labels in each of the dev and test splits, with 100 to 200 labels per failure mode as the plan ([Hamel evals FAQ](https://hamel.dev/blog/posts/evals-faq/)). He says below 60 labeled items the confidence intervals are often too wide ([Hamel: LLM-as-judge](https://hamel.dev/blog/posts/llm-judge/)). Airbnb wants a 50 to 100 item golden set that includes bad examples, and uses a different model for the judge ([Airbnb](https://airbnb.tech/ai-ml/eval-driven-development-lessons-from-evaluating-genai-at-scale/)). The notes flag one source conflict. Airbnb targets percent agreement, while Hamel and Eugene Yan prefer true positive and true negative rates on imbalanced data. Judges are also noisy. One recent single preprint found that about 5% of items flipped verdicts at temperature 0 with a pinned model ([arXiv 2609.33044](https://arxiv.org/abs/2609.33044)). It is not peer reviewed as far as the notes could tell, and it studied pairwise leaderboards, not chat-agent pass/fail.

For trials, Anthropic says each trial should start from a clean environment, because shared state creates correlated failures ([Anthropic: Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). It also says to run several trials, because a task that passed once might fail next time. It defines **pass^k** (all k trials succeed) for consistency, and **pass@k** (at least one of k succeeds) for cases where one success is enough (same page). tau-bench showed why this matters. Its gpt-4o agent scored 61.2 on one retail trial, yet pass^8 fell below 25% ([tau-bench paper](https://arxiv.org/html/2406.12045)). Even at temperature 0, one test gave 80 different completions out of 1,000 ([Thinking Machines](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)). So the suite must treat one result as one draw, and show counts per task.

## The task count, not the trial count, limits what the suite can detect

Evan Miller's paper treats tasks as a sample from a larger unseen population. Its five advice points are: report standard errors, cluster them when tasks are related, resample each task several times, compare versions on the same tasks with paired differences, and run power analysis first ([arXiv 2411.00640](https://arxiv.org/html/2411.00640)). Extra trials only shrink the within-task part of the error. The between-task part stays (same page, as read by the notes). The paper suggests new evals have at least about 1,000 questions, and its example needs about 969 to detect a 3-point difference. Anthropic says 20 to 50 tasks is enough to start because early changes have large effects ([Anthropic: Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Both can be true. A 28-task suite can catch a few tasks collapsing. It cannot see a uniform 1 to 2 point slide. The notes compute that the suite-level detectable change is about 2.6 points if per-task differences have a standard deviation of 0.05, and 10.6 points if it is 0.20. Those standard deviations are assumed, not measured (computed, not sourced).

## A suite keeps changing and sits inside a release process

OpenAI says to "Evaluate early and often" and to set up continuous evaluation that runs evals on every change ([OpenAI: Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)). Hamel says CI evals protect against known regressions before deployment, while production monitoring finds new failures and feeds them back as tasks ([Hamel evals FAQ](https://hamel.dev/blog/posts/evals-faq/)). Anthropic says the same: production monitoring finds drift that synthetic suites miss ([Anthropic: Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)). Intercom's Fin replays a few thousand real past conversations offline, then uses staged rollouts, and follows a rule to never knowingly ship a resolution regression ([Fin](https://ideas.fin.ai/p/why-not-just-ship-it)). GitHub records dataset version, prompt, model and config for every run, and treats eval configs like code ([GitHub: evaluate LLMs before production](https://github.blog/2026-08-25-how-to-evaluate-llms-before-production/)). Fin and GitHub both put cost and latency in the release scorecard beside quality. GitHub's own MCP tool-selection eval is the closest published match to your tool tasks, and GitHub admits thin volume per tool is its weak point ([GitHub MCP offline eval](https://github.blog/ai-and-ml/github-copilot/measuring-what-matters-how-offline-evaluation-of-github-mcp-server-works/)). No source gives a numeric rule for retiring a task, and none gives exact trial counts for a local or CI tier.

## Suite definition checklist

Use this list to review a build. Each item names its source. "Our choice, unbacked" means no note supports it.

1. The suite states its purpose, and every task sits in a labeled group: regression (near 100%) or capability (starts low). Sources: [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [Hamel FAQ](https://hamel.dev/blog/posts/evals-faq/).
2. A written graduation rule moves capability tasks into regression. Anthropic says tasks graduate but gives no threshold. The rule itself: our choice, unbacked.
3. Success criteria are written as numbers before any trial runs. Sources: [Anthropic: Define success](https://platform.claude.com/docs/en/test-and-evaluate/define-success), [OpenAI](https://developers.openai.com/api/docs/guides/evaluation-best-practices).
4. Each task records its origin (real trace, bug report, or synthetic) and a failure-mode tag. Tasks with no observed origin are flagged weak. Sources: [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [Hamel FAQ](https://hamel.dev/blog/posts/evals-faq/), [LangChain](https://www.langchain.com/blog/better-harness-a-recipe-for-harness-hill-climbing-with-evals). The exact tag fields: our choice, unbacked.
5. The suite has 20 to 50 tasks at start. Source: [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).
6. Tasks cover typical, edge and adversarial cases, tagged so coverage is visible. Source: [OpenAI](https://developers.openai.com/api/docs/guides/evaluation-best-practices). Your plan moves security out of scope, so state that in the suite definition.
7. Every "must not" task has a twin where the action should happen. Source: [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).
8. Every task has a reference solution that passes all graders. Two experts would agree on each verdict. A task at 0% over many trials is checked as broken first. Source: [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).
9. Every trial starts in a clean environment. Source: [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).
10. Each task runs several trials. The report shows per-task counts, not only an average. The consistency metric is named (pass^k or pass@k). Sources: [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [tau-bench](https://arxiv.org/html/2406.12045), [Miller](https://arxiv.org/html/2411.00640).
11. Code graders come first. A model judge is used only where code cannot decide. Sources: [Hamel FAQ](https://hamel.dev/blog/posts/evals-faq/), [Vercel](https://vercel.com/i/ai-agent-evaluation-frameworks-production), [Airbnb](https://airbnb.tech/ai-ml/eval-driven-development-lessons-from-evaluating-genai-at-scale/).
12. Each model judge covers one failure mode, gives a binary verdict, and has a labeled set with a held-out test split. Its true positive and true negative rates are recorded. It uses a different model from the agent. Sources: [Hamel FAQ](https://hamel.dev/blog/posts/evals-faq/), [Eugene Yan](https://eugeneyan.com/writing/product-evals/), [OpenAI](https://developers.openai.com/api/docs/guides/evaluation-best-practices), [Airbnb](https://airbnb.tech/ai-ml/eval-driven-development-lessons-from-evaluating-genai-at-scale/).
13. People read transcripts of many trials, and failures look fair. Source: [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).
14. The suite score ships with its standard error and the number of tasks. Version comparisons use the same tasks (paired). Source: [Miller](https://arxiv.org/html/2411.00640).
15. Any pass-rate claim states how many trials back it. A clean result shows the rule-of-three bound next to it. Source: [Rule of three](https://en.wikipedia.org/wiki/Rule_of_three_(statistics)). The specific 97% figures are computed, not sourced.
16. A cheap check runs on every change. A heavier check runs less often. Sources: [OpenAI](https://developers.openai.com/api/docs/guides/evaluation-best-practices), [Hamel](https://hamel.dev/blog/posts/evals/), [Vercel](https://vercel.com/i/ai-agent-evaluation-frameworks-production). The counts of 3 and 10 trials: our choice, unbacked.
17. Every result records dataset version, prompt, model and config. Source: [GitHub](https://github.blog/2026-08-25-how-to-evaluate-llms-before-production/).
18. A named loop turns new production failures into new tasks. Sources: [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [OpenAI](https://developers.openai.com/api/docs/guides/evaluation-best-practices), [Hamel FAQ](https://hamel.dev/blog/posts/evals-faq/), [Fin](https://ideas.fin.ai/p/why-not-just-ship-it).
19. The suite has a named owner and a scheduled cleanup of saturated tasks. Sources: [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents), [LangChain](https://www.langchain.com/blog/better-harness-a-recipe-for-harness-hill-climbing-with-evals). The cleanup schedule: our choice, unbacked.
20. Cost and latency appear beside quality in the release report. Sources: [Fin](https://ideas.fin.ai/p/why-not-just-ship-it), [GitHub](https://github.blog/2026-08-25-how-to-evaluate-llms-before-production/).
21. The release gate is a stated product decision. Source for the idea: [Hamel](https://hamel.dev/blog/posts/evals/). The exact gate (97% per task, at most 3 failures in 100): our choice, unbacked.
22. Errored trials (rate limit, outage) count as neither pass nor fail. Our choice, unbacked.

## Where the current plan conflicts with the sources

I read `backend/evals/eval-design.md`. It has 28 tasks, 3 trials locally with 3 of 3 required, 10 trials in a manual CI job with 9 of 10 required, and a release check over each task's last 100 trials with at most 3 failures. The plan already matches the sources in several places. It uses the Anthropic terms, splits regression from capability, keeps per-task counts, checks judges with true positive and true negative rates, and warns that "clean is not zero". The conflicts below are about the numbers. All probabilities are computed, not sourced. They assume independent trials.

**1. The local bar fails a healthy suite.** If every task truly passes 97% of trials, one task passes 3 of 3 with probability 0.913 (0.97 cubed). All 28 tasks pass 3 of 3 with probability **0.077**. So about 92% of the time, a healthy suite blocks the change. The plan says one flaky task blocks the change, so it will block often. The sources give no trial counts, so this is a design flaw, not a break from a source. The notes also show a task truly at 90% passes 3 of 3 about 73% of the time. The bar is both too strict for the suite and too weak for a single task.

**2. The CI bar is weak per task and strict for the suite.** A truly 97% task passes at least 9 of 10 with probability 0.965. All 28 do so with probability **0.37**. A task truly at 90% still passes with probability 0.74. A task truly at 80% passes with probability 0.38. The plan says these bars "catch broken tasks", and that is fair for a task at 0% or 50%. They cannot tell 97% from 90%.

**3. Observing 97 passes in 100 does not prove 97%.** The rule of three says that with zero failures in n trials, the 95% upper bound on the failure rate is about 3/n ([Rule of three](https://en.wikipedia.org/wiki/Rule_of_three_(statistics))). To back "at most 3% failures" you need about **99 straight passes** (computed). With 97 of 100, the one-sided 95% lower bound on the pass rate is 0.924 (computed). The 3 of 3 result fits a true rate as low as about 37%, and 10 of 10 fits as low as 74% (computed). The plan states the 3/n rule, but its release bar of "at most 3 failures in 100" does not follow from it. That bar uses 97 as a point estimate.

**4. The release bar fails healthy tasks and passes weak ones.** A task truly at 97% has at most 3 failures in 100 with probability only **0.65**. A task truly at 95% still passes with probability 0.26. So the bar cannot tell 95% from 97%. All 28 healthy tasks pass with probability about 5 in a million. The notes report that telling 97% from 94% needs about 746 trials per version (computed). Per Anthropic's own isolation rule, the last 100 trials from ten CI jobs also mix code versions, so they are not draws from one pass rate. That last point is the notes' inference, not a source claim.

**5. Manual-only CI conflicts with "run on every change".** The plan removes the pull-request trigger. OpenAI says to run evals on every change ([OpenAI: Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)). Hamel says CI evals protect against known regressions before deployment ([Hamel evals FAQ](https://hamel.dev/blog/posts/evals-faq/)). The local 3-trial run covers part of this, but it depends on each developer running it. Nothing in the plan forces it.

**6. The plan has no suite-level uncertainty.** All its bars are per task. Miller says to report the standard error and the task count, and to compare versions on the same tasks ([arXiv 2411.00640](https://arxiv.org/html/2411.00640)). With 28 tasks, only large drops are detectable. The plan should say so, and should say which tasks are clustered (for example, tasks built on the same fixture).

**7. Judge noise is not in the 97% math.** The plan checks judges before they gate, which fits the sources. It does not measure how often a judge flips its verdict on the same input. If judged and code-graded tasks share one 97% bar, judge noise lowers the judged tasks' observed rate. The notes suggest reporting them separately and re-running judges 5 or more times. That advice rests on one preprint, flagged above.

**8. Missing pieces the sources ask for.** The plan has no origin tag per task, no failure-mode tag, no graduation rule, no production-failure loop, no dataset-version record, and no cost or latency line (see checklist items 4, 2, 18, 17 and 20). The plan also does not say how many of the 28 tasks are in the regression group and how many are in the capability group.

## Conclusion

The sources agree on what a suite is, and they say little about the exact numbers. No source gives a trial count, a 97% per-task target, or a retirement rule. Those numbers are your choices, and the checklist marks them that way. The statistics are the weak spot. The plan's bars read like proof of a 97% rate, but the computed odds show they act more like smoke alarms. They catch a task at 50%, and they cannot separate 97% from 90%.

The most useful next step is to decide what the suite must prove, then pick bars that match. If the goal is "catch a broken task", the 3-trial and 10-trial bars do that, but the all-28-green rule should change. If the goal is "prove 97%", one task needs about 100 clean trials, and that cost multiplies by 28 tasks. Either way, write the answer into the suite definition before a coding agent builds it.
